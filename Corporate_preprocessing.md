# Корпоративный препроцессинг (Corporate preprocessing)

*← Назад к [[README]]*

#препроцессинг #комплаенс #лимиты

**Корпоративный препроцессинг** — это фаза расширенной обработки, валидации и контроля, следующая за [[Base_preprocessing|Базовым препроцессингом]]. Выполняется на уровне **Corporate Transfer Hub** и добавляет сложную бизнес-логику для корпоративных клиентов.

Задачи расширенного препроцессинга:
- комплексный биллинг и тарификация
- обеспечение внутреннего комплаенса

**Комплексный биллинг и тарификация**  реализует более сложные схемы тарификации:
- **Многосторонние комиссии** с участием нескольких получателей
- **Механизмы компенсации** (кэшбэк, рибейты, партнерские вознаграждения)
- **Динамические тарифы** на основе объемов и времени
- **Валютные конвертации** с гибкими курсами и спредами
(подробнее в отдельной заметке).

**Внутренний комплаенс** — это система контроля соблюдения внутренних договорных обязательств, партнерских соглашений и корпоративных политик, которые выходят за рамки стандартных лимитов участника. Соблюдение комплаенса достигается путём применения бизнес-правил, определенных в договорах с партнерами и представленных в специальном (внутреннем) формате (aka limit config).

**Динамический лимит** - это агрегированное значение, вычисляемое на основе контекстно-зависимых правил и учитывающий историю операций.

В отличие от базового уровня, который проверяет общие условия обслуживания участника, корпоративный препроцессинг оперирует сложными бизнес-сценариями и требует интеграции с системами хранения исторических данных.

## Архитектурные вызовы динамических ограничений

### Протяжённость во времени и многоэтапность
Динамические лимиты должны вычисляться, применяться и фиксироваться на различных этапах обработки операции:
- **pre-routing**
- **post-routing**
- **post-processing**

### Проблема конкурентного доступа (Race Condition)
Конкурентное выполнение операций может приводить к превышению установленных ограничений и нарушению комплаенса, поэтому учёт лимитов должен упорядочиваться за счёт, например, механизмов холдирования.
> Такой механизм в свою очередь может приводить к падению конверсии, когда некоторые операции будут откланяться из-за временно захолдиованных лимитов, но глобально это компенсируется отсутствием штрафных санкций

**Механизм холдирования лимитов:**
- **Резервирование:** Лимиты холдируются на всех участниках и провайдерах-кандидатах
- **Атомарность:** Предотвращение превышения лимитов в условиях конкурентного доступа
- **Освобождение ресурсов:**
  - При успехе: холд фиксируется на исполнителе, откатывается на остальных
  - При неуспехе: все холды откатываются

**Пример сценария:**
```
1. Операция 1000 USD → холдирует лимиты у Мерчанта A, Провайдера B, Провайдера C
2. Выполнение через Провайдера B → успех
3. Холд фиксируется у Мерчанта A и Провайдера B
4. Холд откатывается у Провайдера C
```

## Объект ограничений (что может быть ограничено)

- сумма операций за период
- количество операций за период
- что-то еще???
> в качестве периода могут выступать: календарный отрезок времени, скользящее окно, произвольные отрезки времени по расписанию и т.д.

## Критерии, для установки ограничений

### Канальные ограничения

- **Идентификатор провайдера:** лимит устанавливается на все операции через провайдера независимо от типа канала
- **Идентификатор канала:** лимит устанавливается на операции через определёный тип канала

### Бизнес-контекст

#### Бизнес-контекст обобщенный

- **Тип операции**

#### Бизнес-контекст обычного платежа

- **Категория мерчанта:** MCC-код, тип деятельности, отрасль
- **Продуктовая категория:** Тип товара/услуги, стоимостная категория
- **Канал продаж:** Онлайн, POS, мобильное приложение, call-center (не путать с каналом проведения трансфера)

#### Бизнес-контексты иных операций

### Идентификационные данные участника

- **Финансовые реквизиты:** Номер карты, банковский счет, криптоадрес
- **Персональные данные:** Email, телефон, адрес доставки
- **Устройство и сессия:** Device fingerprint, IP-адрес, браузер
- **Биометрические данные:** Для операций с биометрической идентификацией
- **Идентификатор участника**

## Комбинация критериев (многофакторная группировка)

Реальное бизнес-правило может осуществлять группировку по любым (применимым) критериям для любого периода времени.

## Мультиуровневые одобрения

**Система эскалации** для операций, требующих дополнительных одобрений:

**Уровни одобрения:**
- **Автоматическое одобрение:** В рамках предустановленных лимитов
- **Одобрение менеджера:** Для операций среднего риска или размера
- **Одобрение комитета:** Для крупных или нестандартных операций
- **Регуляторное одобрение:** Для операций, требующих внешних согласований

## Интеграция с корпоративными системами

Интеграция с внутренними система обеспечивает автоматическое или автоматизированное (то есть требующее подтверждение сотрудника) создание внутреннего представления бизнес-правил (конфигурация лимитов).

#### ERP-системы:
- **Проверка бюджетов:** Наличие средств в соответствующих статьях бюджета
- **Обработка договоров:** автоматизированное формирование внутреннего представления бизнес-правил при регистрации договора
- **Учетная политика:** Соблюдение внутренних учетных правил и процедур (аналогично обработке договоров, при добавлении правил и процедур автоматически генерируются конфигурации для них)

#### HR-системы:
- **Полномочия сотрудников:** Право на инициацию операций определенного типа
- **Организационная структура:** Проверка подчиненности для внутренних переводов
- **Статус сотрудника:** Активность, отпуск, увольнение для зарплатных операций

#### CRM-системы:
- **Категория клиента:** VIP-статус, льготные условия, особые требования
- **Жизненный цикл клиента:** Onboarding, активность, churn risk

## Результат корпоративного препроцессинга

### Расширенные метаданные:
- **Результаты проверок** с детализацией по лимитам
- **Статус одобрений** и цепочка ответственных лиц
- **Данные интеграций** с корпоративными системами

### Дополнительные ограничения:
- **Временные блокировки** при достижении лимитов
- **Условия выполнения** (время, дополнительные подтверждения)
- **Мониторинговые триггеры** для последующего анализа
- **Эскалационные процедуры** при возникновении исключений

## Отличия от базового препроцессинга

| Аспект | Базовый препроцессинг | Корпоративный препроцессинг |
|--------|----------------------|---------------------------|
| **Лимиты** | Статические лимиты участника | Динамические лимиты за период |
| **Группировка** | Простая (по участнику/активу) | Многофакторная группировка |
| **Одобрения** | Автоматические | Мультиуровневая эскалация |
| **Интеграции** | Внешние scoring системы | Корпоративные ERP/HR/CRM |
| **Отчетность** | Базовый аудитный след | Данные для комплаенс-отчетности |
