# Change Data Capture (CDC)
*← Назад к [[README]]*

#архитектура #cdc

**Change Data Capture (CDC)** — это специализированный компонент, отвечающий за отслеживание изменений состояния объектов в ядре процессинга ([[Transfer_Engine]]) и их асинхронную, надежную доставку в ядро пост-обработки и аналитики (Бэкофис, отчетность, мониторинг, долгосрочное хранение).

Его основная задача — обеспечить консистентность данных между гетерогенными подсистемами с разными моделями данных и нагрузками, минимизируя impact на производительность ядра процессинга.

**Задачи компонента CDC**
1. Детектирование изменений
2. Минимальное воздействие: Обеспечение отслеживания изменений с минимальной нагрузкой на источник
3. Гарантированная доставка: Обеспечение доставки каждого события об изменении в системы пост-обработки с требуемой стратегией доставки
4. Структурирование данных: Преобразование "сырых" изменений в структурированные бизнес-события, понятные потребителям
5. Буферизация и балансировка: Сглаживание пиковых нагрузок и обеспечение надежности доставки даже при временной недоступности систем-потребителей

## Проблема версионирования форматов данных

**Архитектурые особенности реализации на примере потомков RBK.money** - в системе хранения полезная нагрузка (бизнес-сущности, бизнес-события) хранится в непрозрачном для нее формате, не имеет заданной схемы и не может обрабатываться средствами самой СУБД.

**Архитектурное требование** - система-потребитель может получать данные не только через CDC, но и путем синхронных запросов к API системы-источника, требование заключается в том, что формат предаставления данных должен быть одинаков для обоих каналов получения информации.

В ходе эксплуатации систем многие сущности (обрабатываемые и хранимые) могут эволюционно развиваться, приобретать новые свойства и утрачивать старые. С точки зрения платформ это выглядит как изменение формата объекта в представлении API, изменении схемы хранения (если применимо) и т.п. Традиционно требование единства форматов для разных каналов решается следующими способами:
- **миграция хранения:** при обновлении формата представления осуществляется миграция в БД, миграция БД и обновление зависимых компонентов выполняется согласованно
- **миграция при чтении:** в случае невозможности или сложности миграций БД в систему внедряется компонент, ответственный за мапинг версий, в остальном обновление формата представления аналогично миграции, только вместо миграции - обновлеие компонента-маппера. "Приближение" маппера к БД позволяет соблюсти **принцип единичной ответственности** и не разамазывать функциональность по системе

### "Проблема" с Kafka как с источником исторических данных

В сценарии применения Kafka, когда она смешивает стримы в реальном времени с историческими стримами возникает ситуация, что данные в рамках одного топика хранятся в смешанном формате (разные версии формата представления). Если топик будет использован для перевычитки исторических данных, то это в свою очередь приводит к необходимости "размазывания" функций маппинга форматов на каждого читателя.

Для исключения этой проблемы есть два пути:
1. Использовать Kafka в режиме "прочитал - забыл", то есть как классический брокер сообщений, а не персистентный лог. То есть Kafka является чистым транспортом (но со встроенной поддержкой буферизации и кэширования). Исторические данные запрашиваются по необходимости у CDC, он в свою очередь вычитывает из БД и стримит в актуальном формате представления. В этой схеме и стрим в реальном времени и запрошенные исторические данные содержат не только информацию о факте изменения бизнес-сущности, но и сами данные бизнес-сущности (стейт) в актуальном формате представления  (как при этом осуществляется мапинг старых форматов - это не проблема потребителей).
2. Разделить исторические топики от данных в реальном времени. То есть, стримы реального времени работают в режиме "прочитал-забыл", как и в первом варианте в них присутствует стейт бизнес-сущности, которую обрабатывает потребитель, в формате актуальном для всей системы. Исторические топики хранят всю свою историю сообщений, но при этом не содержат данных с изменяемым форматом (стейт бизнес-сущности), а только информацию о самом факте прогресса (то есть идентификационные данные сущности, дата-время, идентификатор события/значение новой версии стейта (не путать с версией формата представления)). На основе данных, содержащихся в историческом топике, потребитель может сделать синхронный запрос в API системы-источника для получения определённой версии стейта в текущем актуальном формате представления.

В первом варианте все стримы инициируются по запросу потребителя (для этого, например, CDC может читать свой топик, в котором будут запросы на старт/останов стриминга в определенные топики потребителей и параметры стримов (тут возможно будет сделать гибче, чем в текущей реализации, например стримить не за весь неймсейс, а с фильтрацией по каким-то параметрам)).

Во втором варианте CDC должен безусловно стримить данные в исторические топики и стартовать стримы в реальном времени по запросу потребителей.
