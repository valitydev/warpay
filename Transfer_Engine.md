# Трансферный движок (Transfer Engine)

*← Назад к [[README]]*

#архитектура #трансфер

**Трансферный движок** — это универсальный слой системы, который получает цепочки трансферов от слоя бизнес-сервисов ([[High_Level_Design]]) и обеспечивает их выполнение через специализированные адаптеры провайдеров.

## Терминология

### Цепочки трансферов (Transfer Chains)

**Цепочка трансферов** — это совокупность взаимосвязанных трансферов, которые могут группироваться и выполняться с различными стратегиями. Цепочка представляет собой логическую единицу операций, поступающую от слоя бизнес-сервисов в трансферный движок.

#### Структура цепочки

Цепочка представляет собой **рекурсивный тип**, который может содержать как индивидуальные трансферы, так и вложенные цепочки. Каждая цепочка выполняется с определенной стратегией:

```json
{
  "chain": {
    "chain_id": "chain_12345",
    "strategy": "AllOf",
    "execution": "parallel",
    "items": [
      {
        "transfer": {
          "transfer_id": "tf_001",
          "source": {...},
          "destination": {...},
          "asset": {"type": "fiat", "currency": "USD", "amount": "5000.00"},
          "details": {...}
        }
      },
      {
        "chain": {
          "chain_id": "nested_chain_001",
          "strategy": "OneOf",
          "execution": "sequential",
          "items": [
            {
              "transfer": {...}
            },
            {
              "transfer": {...}
            }
          ]
        }
      }
    ]
  }
}
```

#### Стратегии выполнения цепочек

**AllOf (Все или ничего):**
- Все элементы в цепочке (трансферы и вложенные цепочки) должны завершиться успехом
- При неудаче любого элемента вся цепочка считается неуспешной
- Поддерживает компенсирующие транзакции для отката выполненных операций
- Используется для критичных операций, где частичное выполнение недопустимо

**AnyOf (Хотя бы один):**
- Хотя бы один элемент в цепочке должен завершиться успехом
- Попытка выполнения производится для всех элементов в цепочке
- Цепочка считается успешной, если выполнен минимум один элемент
- Используется для операций с несколькими альтернативными вариантами

**OneOf (Первый успешный):**
- Выполнение элементов происходит до первого успешного
- После успешного выполнения одного элемента остальные не выполняются
- Цепочка считается успешной при успехе любого элемента
- Используется для операций с приоритетными альтернативами

#### Порядок выполнения

**Параллельное выполнение:**
- Все элементы в цепочке (трансферы и вложенные цепочки) запускаются одновременно
- Сокращает общее время выполнения
- Подходит для независимых операций

**Последовательное выполнение:**
- Элементы выполняются строго по порядку
- Следующий элемент запускается только после завершения предыдущего
- Обязательно для операций с зависимостями

#### Зависимости между элементами

Элементы в цепочке могут иметь зависимости друг от друга:
- **Строгая последовательность:** Элемент запускается только после успешного завершения всех зависимых элементов
- **Условные зависимости:** Запуск элемента зависит от результата выполнения предыдущих элементов
- **Рекурсивная обработка:** Вложенные цепочки обрабатываются по тем же правилам с собственными стратегиями

> ОБСУДИТЬ! Реализация отката при неуспехе цепочки будет зависеть от высокоуровневой логики, то есть трасферный движок при неуспехе возвращает на бизнес слой лог выполнения цепочки, на основании которого бизнес слой должен сформировать компенсирующую цепочку. В простейшем варианте, когда успешно выполнено N трансферов, а N+1 неудался, можно автоматически сформировать "зеркальные" трансферы для N успешных, но это не будет равно возврату в исходное состояние, так как провайдер снимет свою комиссию за обе операции, то есть должна быть корректировка на размер комиссии для кого-то из участников. В другом варианте, когда канал проведения допускает холдирование средств, то все операции коммитятся только после успешного холдирования, иначе откатываются (позволяет обойтись без сложного сценария компенсации). Но цепочка может использовать разнородные каналы, как с поддержкой холдирования, так и без. На начальном этапе  ответственность за компенсирующие транзакции можно возложить на бизнес-слой, а на уровне движка трансферов уметь сначала холдировать по всей цепочке, где возможно, а потом коммитить.

## Взаимодействие с другими компонентами

### Business Services Layer → Transfer Engine

**Слой бизнес-сервисов** выполняет операции **препроцессинга** и преобразует конкретные финансовые операции к виду цепочки обобщенных трансферов. В процессе преобразования:

- **Инкапсуляция специфики:** В цепочки трансферов инкапсулируются специфические детали операции (правила валидации, бизнес-ограничения, регуляторные требования)
- **Абстракция сложности:** Сложные финансовые операции разбиваются на последовательность простых трансферов
- **Определение стратегий:** Устанавливаются стратегии выполнения (AllOf/AnyOf/OneOf) и порядок исполнения

### Transfer Engine → Provider Adapters

**Transfer Engine** получает цепочки трансферов и:

- **Составляет план исполнения** с учетом зависимостей, стратегий и доступных каналов
- **Обеспечивает выполнение** через специализированные адаптеры провайдеров
- **Управляет состоянием** выполнения каждого элемента цепочки
- **Координирует транзакции** между различными провайдерами

### Асинхронные результаты

Результаты исполнения цепочек трансферов **отправляются в шину/брокер сообщений** (не показан на архитектурной схеме) для:

- **Уведомления бизнес-сервисов** о завершении операций
- **Интеграции с внешними системами** (учет, отчетность, аудит)
- **Обработки событий** другими компонентами системы

### Синхронные запросы

**Бизнес-слой может делать синхронные запросы** для получения:

- **Текущего статуса** выполнения цепочки трансферов
- **Детального состояния** каждого элемента в цепочке
- **Информации о ходе исполнения** и промежуточных результатов
- **Диагностической информации** при возникновении ошибок

## Основные компоненты Transfer Engine

Transfer Engine состоит из четырех ключевых компонентов: **Routing Engine**, **Transfer Processor**, **Transfer Chain Processor** и **State Management**.

### Routing Engine

Отвечает за интеллектуальную маршрутизацию трансферов через оптимальные каналы провайдеров.

#### Route Calculator

Предназначен для:
- **Анализ доступных каналов** для заданной пары участников и типа актива
- **Расчет стоимости, времени и надежности** каждого маршрута
- **Учет лимитов провайдеров и участников**
- ??? **Поддержка multi-hop маршрутизации** ??? > ИИ предложил, что бы это могло быть

#### Load Balancer

Обеспечивает:
- **Распределение нагрузки** между провайдерами
- **Мониторинг доступности каналов** в реальном времени
- **Динамическое переключение при сбоях**

### Transfer Chain Processor

Управляет обработкой цепочек трансферов. Основные функции:

- **Создание плана исполнения** для полученной цепочки трансферов с учетом зависимостей и стратегий
- **Инициация атомарных трансферов** в соответствии с планом выполнения
- **Отслеживание результатов исполнения** и координация между различными элементами цепочки

### Transfer Processor

Обеспечивает выполнение атомарных трансферов через адаптеры провайдеров:

- **Исполнение индивидуальных трансферов** согласно выбранным маршрутам
- **Взаимодействие с адаптерами провайдеров** для фактического проведения операций
- **Обработка ответов** и статусов от внешних систем

### State Management

Компонент для управления прогрессом процессоров и сохранения их стейта:

- **Сохранение промежуточного состояния** всех трансферов и цепочек в процессе выполнения
- **Планирование активности** и координация временных зависимостей
- **Активация процессоров** в соответствии с планом и изменениями состояния
- **Event sourcing** для обеспечения аудитного следа и возможности восстановления
- **Реализация паттернов устойчивости** (retry, circuit breaker, timeout)
- **Уведомления об изменениях** состояния для других компонентов системы

### Масштабирование и производительность

#### Горизонтальное масштабирование
- **Stateless компоненты:** Routing Engine, Transfer Chain Processor
- **Stateful компоненты:** State Management с sharding по chain_id/transfer_id
- **Database sharding:** Разделение по участникам или временным интервалам

#### Кэширование
- **Route cache:** Кэширование оптимальных маршрутов для частых пар участников
- **Provider capability cache:** Кэширование возможностей и лимитов провайдеров
- **Exchange rate cache:** Кэширование курсов валют для cost calculation

#### Асинхронная обработка
- **Message queues:** Для обработки долгих операций
- **Event-driven architecture:** Реакция на изменения состояний
- **Batch processing:** Группировка мелких трансферов для оптимизации

#### Graceful Degradation
Система должна продолжать работать даже при частичных сбоях:
- Автоматическое переключение на резервные каналы
- Откладывание некритичных операций
- Уведомление пользователей о снижении качества сервиса

### Безопасность

#### Аутентификация и авторизация
- **mTLS** для связи между компонентами
- **JWT tokens** с коротким сроком жизни
- **RBAC/ABAC** для доступа к различным операциям

#### Шифрование
- **Encryption at rest:** Все персональные данные и финансовая информация
- **Encryption in transit:** Все API calls и webhook notifications
- **Key rotation:** Регулярная ротация ключей шифрования

#### Audit Trail
- **Immutable log** всех операций
- **Digital signatures** критичных транзакций
- **Compliance reporting** для регуляторных требований
